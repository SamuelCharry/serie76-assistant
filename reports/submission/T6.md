### Scorer correction and numeric serialization

Pydantic NumericBound.value is Decimal, and production validation dumps mode="json" before context/trace persistence. JSON-mode Decimal becomes a string such as "70"; this is intentional lossless serialization, not an OCR, SQL or persistence bug. Canonical validation reads that representation back as Decimal. Changing it to float would discard precision unnecessarily.

The comparator only bridges representations for the nine numeric bound fields. Decimal-normalised values must be equal; booleans, non-finite values, malformed/extra bound keys and wrong operators fail. Explicit value/op expectations require both. Legacy scalar minimum expectations accept a gte object only when the current/prior case query actually says at least/minimum for the same numeric value; a gt/lt/lte object never passes that fallback. Other dimensions, filters, products, answer text, tools and clarification checks retain their checks. Inclusive legacy scalar actual arguments retain the repository's original min/max defaults only when matching an explicit inclusive expectation.

The old report command reused saved passed/failures/status fields instead of recomputing them. It now deep-copies recorded observations, checks exact query alignment, rehydrates recorded product/term identifiers, scores each turn and recomputes non-provider scenario status without running models, tools, SQL or rendering. It preserves provider-failure disposition and refuses incomplete or mismatched non-provider records. Older recordings omitted the SQL candidate list: those candidate-only checks retain their original verdicts (explicitly disclosed in the summary); they are not independently revalidated or fabricated from today's catalogue. All other checks are recomputed. Future recordings now retain candidates. [Eight offline scorer/report tests](../../tests/test_acceptance_scoring.py) include operator strictness, unchanged unrelated checks and byte-for-byte evidence preservation.
